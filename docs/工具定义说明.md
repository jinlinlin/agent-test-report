# 工具定义说明（交付物 #3）

> 对应需求文档 §4 F1–F8、§7 统计契约。工具层位于 `report_agent/tools/`，均继承 `Tool` 基类，统一返回 `ToolResult(ok, data, error, meta)`；异常在工具内部捕获转 `ok=False`，保证 ReAct 循环不崩溃。规划器通过 `ToolRegistry.specs()` 读取每个工具的 `name/description/parameters` 作为可选动作。

## 工具总览

| 工具名 | 类 / 文件 | 需求 | 入参 | 关键返回 |
|--------|-----------|------|------|----------|
| `get_version_info` | `GetVersionInfoTool` / `zentao_version.py` | F1 | `version_name: string` | `data{name,description,test_start,test_end,product_id,build,fetch_status}` |
| `get_version_bugs` | `GetVersionBugsTool` / `zentao_bugs.py` | F2 | `version_name: string` | `data[bug...]`、`meta.count` |
| `compute_statistics` | `ComputeStatisticsTool` / `statistics.py` | F3、F8 | `version_info`、`bugs`（循环注入） | `data=StatsResult.to_dict()`、`meta.stats_obj` |
| `render_report` | `RenderReportTool` / `render_report.py` | F4 | `stats_obj`（循环注入） | `data=Markdown 文本` |
| （mock 数据源） | `mock_zentao.py` | F6 | `fault`（配置项） | 版本/缺陷桩数据 + 故障分支 |

> `compute_statistics`/`render_report` 的重对象由 `loop._exec_tool` 注入，不要求 LLM 搬运。

## 1. get_version_info（F1）

- **mock**：`mock_zentao.fetch_version`，精确全名匹配已知版本。
- **live**：账号/Token 换禅道 REST token → `parse_version` 拆「产品关键字 + 版本号」→ `find_product` 定位 product。只读（F7，仅 GET）。
- **失败映射**：`ZentaoError.kind` → `fetch_status ∈ {timeout, not_found, error}`，`ok=False`；产品未找到 → `not_found`。
- 返回 `build` 字段供统计层做「测试起止时间精确版本匹配」。

## 2. get_version_bugs（F2）

- **live 流程**：定位 product → `get_product_bugs`（固定带 `status=all` 才能含已关闭，以 `response.total` 终止分页）→ 按 `openedBuild`「包含即计入」过滤本版本 → 逐条 `get_bug` 补拉 `moduleTitle` 作模块名。
- **版本存在性判定（V1-002）**：指定了版本号但该产品全部缺陷 `openedBuild` 均不含它 → `ok=False`、`fetch_status=not_found`、`count=0`，终止不编造。（live 下「版本存在但零缺陷」不可与「不存在」区分，按不存在处理；零缺陷由 mock `empty_bugs` 覆盖。）
- **归一化 `_normalize`**：禅道字段按 `settings.yaml` 的 `field_*` 映射为内部 schema：`{id,module,severity,status,resolution,activatedCount,openedDate,openedBuild}`。

## 3. compute_statistics（F3 + F8 规则引擎）

- 纯函数 `compute_statistics(version_info, bugs)` → `StatsResult`（结构见 §7 契约）：
  - `summary`：总数、四态计数、修复覆盖率（已关闭÷总数，两位小数，延期计入分母）、激活≥1 次数与激活率；
  - `module_distribution`：按模块路径原样分组、**不合并**（U-008），按总数降序，含总计；
  - `level_status_distribution`：P1–P4 × 四状态交叉（激活口径=`status=active`）；
  - `conclusion`：由 `rules/release_engine.evaluate` 产准入判定（P1 激活=0；P2 激活占比≤5%；P3≤30%；P4 不限）+ 证据；
  - `integrity`：`data_complete` 取决于 `fetch_status==ok`；测试起止缺失仅软性标注 `missing_fields`，不阻断结论。
- **四类分桶 `status_bucket` 互斥优先序**：`closed`→已关闭（最高优先）；`active`→待解决；非 closed 且 `resolution=postponed`→延期；`resolved` 且非 postponed→待验收。

## 4. render_report（F4）

- 先产本地图表（注入 `cfg` 且 `charts.enabled` 时）：`report/charts.render_charts` 按 StatsResult 契约数据用 matplotlib 生成五张数据图 PNG（4.1 状态条形柱状图、4.2 激活次数水平柱状图、4.3/4.4 每人提交/解决水平柱状图、4.5 等级饼图；4.1.1 模块分布仅表格不出图）到 `output/assets/<版本>/`；渲染层 `render_report(stats_obj, charts)` 以相对路径引用图片，缺 key / 未启用 / 未注入 cfg 时回退 `CHART_PLACEHOLDER` 占位文字，**不阻断渲染**。
- **渲染层不做任何计算**，只把结构化数值搬进 Markdown，图中数值与表格同源（只取契约字段）；章节按 §6.1 裁剪表，占位章节用表格骨架/占位符；4.3/4.4 每人件数由统计工具按 openedBy/resolvedBy 实算（`people.submit_counts`/`resolve_counts`），无数据时如实回退占位。
- `stats_obj` 为空 → `ok=False`（缺统计无法渲染）。
- 失败/超限另有 `render_failure_report` / `render_step_limit_report`（§5.3），不含任何虚构数据。

## 5. mock 数据源与故障注入（F6）

- `MOCK_VERSIONS`/`MOCK_BUGS` 内置 `UniResearch V5.0.0` 的 24 条代表性缺陷，覆盖各模块/等级/状态/resolution/激活次数分支。
- `fault` 开关（CLI `--fault` 或 `settings.yaml` `mock.fault`）：
  - `none` 正常；`not_found`/`timeout`/`error` 令 `fetch_version`/`fetch_bugs` 返回对应失败；
  - `empty_bugs` 令缺陷为空（`ok=True, data=[]`）验证 V1-004 全 0 统计。
- `agent.max_steps` 可调小以稳定触发 V1-005 步数超限。

## 6. 只读保障（F7）

live 全流程仅使用 GET（`/products`、`/products/{id}/bugs`、`/bugs/{id}`、`/products` 详情），无任何写端点；凭据走本地 `config/.env`（`ZENTAO_TOKEN`/`ZENTAO_ACCOUNT`/`ZENTAO_PASSWORD`），已被 `.gitignore` 排除。可用 `python -m report_agent.main --probe` 核验认证/端点/真实字段名。
