# 测试报告生成 Agent V1.0 需求文档

> 目标：打通 Agent 执行链路，实现禅道数据获取、独立工具统计、精简版报告输出。

---

## 1. 目标

- **跑通确定性主链路**：输入版本名称 → Agent 自行规划取数顺序 → 获取禅道版本信息 → 获取版本原始 Bug 列表 → 调用独立统计工具计算指标 → 按章节结构输出 Markdown 报告。
- **重点验证组件行为**：LLM 规划推理、工具调用、短期记忆 State、循环控制器、终止条件、异常兜底。
- **守住输出边界**：报告只覆盖版本与缺陷数据；结论与发布建议必须由统计数字推出；测试范围、测试环境、参考文档、测试人员均使用占位符；不接入飞书；不渲染图片/图表（图表章节转为数值 + Markdown 表格）。
- **留下比对证据**：完成正常版本、版本不存在、取数超时、缺陷为空、执行超限五类场景验证，以 V1-001 的完整 Trace 与一份样例报告作为验收证据。
- **学习定位**：本项目以掌握单 Agent 开发全流程为首要目标，V1.0 为最小闭环，多源接入与人机交互留待 V2/V3。

---

## 2. 输入输出定义

### 2.1 用户输入
- **格式**：自然语言传入版本名称。
- **示例**：`帮我生成 UniResearch V5.0.0 的测试报告`
- **版本名匹配口径**：采用**精确全名匹配**（含项目前缀，如 `UniResearch V5.0.0`）。匹配不到即按「版本不存在」处理，不做模糊匹配、不做多候选交互（留待 V2）。
- **缺失处理**：输入未包含可识别版本名称时，触发一次澄清；澄清后仍缺失则终止（见 V1-007）。

### 2.2 Agent 输出
- **正常场景**：Markdown 格式精简测试报告，章节结构以 `docs/UniResearch V5.0.0 测试报告.docx` 为准，按第 6 章「章节裁剪对照表」保留/占位/裁剪。
- **异常场景**：失败说明版报告（结构见 5.3），如实标注失败环节与原因，不含任何虚构数字、链接与业务描述。

## 3. 口径与规则

### 3.1 统计口径

| 口径项 | 定义 |
|--------|------|
| 缺陷总数 | 该版本关联缺陷的全部条目，包含所有状态，不做剔除 |
| 待解决 | 仍处于激活/处理中、尚未提交验证的缺陷（status=active） |
| 待验收 | 研发已修复并提交验证、尚未回归确认的缺陷（status=resolved） |
| 已关闭 | 回归验证通过并完成关闭的缺陷（status=closed） |
| 延期 | 经评审确认不在本版本修复、转入后续版本的缺陷（status≠closed 且 resolution=postponed） |
| 修复覆盖率 | 已关闭缺陷数 ÷ 缺陷总数；延期计入分母；结果保留两位小数（样例 `287/343=83.67%`）；仅作修复进展展示，**不作为发布准入门槛**（门槛见 3.3） |
| 缺陷等级 | P1 致命、P2 严重、P3 一般、P4 建议，以缺陷单登记等级（severity/priority）为准 |
| 测试起止时间 | 取版本提测时间与测试完成时间，不采用缺陷提交时间 |

### 3.2 禅道状态映射表

> 下表为统计工具的状态归类依据，映射逻辑集中在统计工具，禁止散落在提示词。评审时与禅道实际字段核对后可微调。

| 本文口径 | 禅道 status | 禅道 resolution | 备注（优先级自上而下，互斥） |
|----------|-------------|-----------------|------|
| 已关闭 | `closed` | 任意 | **优先级最高**：status=closed 一律计已关闭，即使 resolution 为延期处理 |
| 待解决 | `active` | — | status=激活 |
| 延期 | ≠`closed` | `postponed`（延期处理） | 仅认 postponed；willnotfix/deferred 等不再算延期 |
| 待验收 | `resolved` | ≠`postponed`（fixed/willnotfix/bydesign/duplicate/notrepro/external 等） | 已解决且非延期处理 |

> 归类逻辑集中在 `statistics.status_bucket`，禁止散落在提示词。判定顺序：`closed`→已关闭；`active`→待解决；`resolved 且 postponed`→延期；`resolved 且 非 postponed`→待验收。

### 3.3 业务规则

- **发布准入标准**：以缺陷**激活（待解决，status=active）**数量为分子、**缺陷总数**为分母，占比保留两位小数：
  - **P1 致命**：激活缺陷数必须为 **0**（不允许存在未解决的 P1 缺陷）；
  - **P2 严重**：激活缺陷数 ÷ 缺陷总数 **≤ 5%**；
  - **P3 一般**：激活缺陷数 ÷ 缺陷总数 **≤ 30%**；
  - **P4 建议**：不做限制，可延期。
  - 判定：四项全部满足 → 可发布；任一不满足 → 阻断/暂缓，并输出命中的具体依据。
- **只读原则**：仅查询，不得新增、修改、关闭任何缺陷（技术保障见 F7）。
- **防幻觉**：取数失败时如实标注失败，禁止补造数字、链接与业务描述；报告数字一律以统计工具实算为准，禁止复制样例文案中的数字。
- **执行上限**：配置最大执行步数，防止反复重试导致死循环；步数计数口径：一次工具调用 = 一步，一次 LLM 推理规划 = 一步。

## 4. 功能需求

| 编号 | 功能 | 需求要点 | 关联验收 |
|------|------|----------|----------|
| F1 | 版本基础信息获取 | 按版本名称精确匹配，取得版本描述与测试起止时间，用于报告「执行结果」章节 | A1 |
| F2 | 版本缺陷明细获取 | 取得该版本全部缺陷，覆盖模块归属、优先级/等级、当前状态、resolution、激活次数等字段 | A1 |
| F3 | 缺陷统计汇总 | 由独立统计工具完成总量、状态分布、模块分布、等级×状态交叉分布、修复覆盖率计算，不交由模型自行汇总；输出遵循第 7 章 JSON Schema | A1 |
| F4 | 测试报告生成 | 按第 6 章章节裁剪对照表输出 Markdown；结论与发布建议由 F3 结构化数据填充，LLM 不再计算 | A1、A2 |
| F5 | 异常与终止处理 | 版本不存在、取数失败、缺陷为空、执行超限四类情况须可识别、可终止、不产出伪造内容；失败时输出失败说明版报告 | A3 |
| F6 | 故障注入能力 | 禅道工具层支持 mock 模式，配置化模拟「超时 / 报错 / 空数据 / 版本不存在」；最大执行步数做成配置项，可调小以稳定触发 V1-005 | A3 |
| F7 | 只读权限保障 | 禅道接入使用只读 Token；验收时核验 Token 权限范围或审计操作日志，确认无写操作 | A3 |
| F8 | 发布建议规则引擎 | 在统计工具内以确定性规则实现准入判定（激活 P1=0；激活 P2 占比 ≤5%；激活 P3 占比 ≤30%；P4 不限），输出「测试结论 + 发布建议 + 命中的具体缺陷状态依据」 | A2 |

## 5. 处理流程

### 5.1 主链路

| 环节 | 输入 | 输出 | 失败处理 |
|------|------|------|----------|
| 任务规划 | 版本名称 | 待取数据清单 | 缺版本名先澄清一次；仍缺失则终止（V1-007） |
| 版本信息获取 | 版本名称 | 版本描述、测试起止时间 | 版本不存在/取数失败 → 终止规划，转失败说明版报告 |
| 缺陷明细获取 | 版本名称 | 缺陷条目：模块、等级、状态、resolution、激活次数 | 取数失败 → 终止，转失败说明版报告；不编造 |
| 统计汇总 | 缺陷条目 | 总量、状态、模块、等级×状态、覆盖率 | 空数据输出全 0，不推断（V1-004） |
| 结论判定 | 统计数据 + 准入标准 | 测试结论与发布建议（规则引擎输出） | 数据不完整时不输出结论，只说明缺口 |
| 报告输出 | 结论 + 统计数据 | Markdown 报告 | 占位章节标注「待补充」，不擅自编写 |

### 5.2 终止条件
- 版本不存在 / 取数失败 → 立即终止，不循环重试。
- 缺陷为空 → 正常走完全链路，统计全 0，仍按准入标准给发布建议。
- 执行步数达上限 → 立即终止，输出超限说明版报告。

### 5.3 失败/异常报告结构
异常场景产出的报告为**合法交付物**，仅含：
1. 一句话结论（如「获取禅道数据失败，无法完成缺陷统计」/「执行步数超限，报告生成不完整」）；
2. 失败环节与原因（版本不存在 / 超时 / 报错 / 步数超限）；
3. 明确的缺口说明（哪些章节未能生成）。

不得包含任何虚构的缺陷数字、模块分布、链接或业务描述。

## 8. 验证与验收

验收拆为两层：**E2E 用例（V1-xxx）**验证整链路，**单元测试用例（U-xxx）**验证统计工具纯函数。本期交付证据为 V1-001 的完整 Trace 与样例报告各一份。

### 8.1 E2E 用例

| 用例 ID | 场景 | 预期结果 | 对应验收 |
|---------|------|----------|----------|
| V1-001 | 正常版本，缺陷数据完整 | 按序取数与统计；统计数值与源数据逐项一致；报告章节按裁剪表完整；发布建议符合准入标准且附证据；Trace 可见完整链路 | A1、A2 |

| V1-003 | 禅道接口超时/报错（F6 mock 触发） | 与 V1-002 一致，禁止幻觉填充数据 | A3 |

### 8.3 验收口径
- **A1 数据一致**：正常版本一次请求即产出完整报告，统计数值与源数据逐项可核对（覆盖率两位小数）。
- **A2 结论可解释**：发布建议能对应到 `conclusion.evidence` 中的具体缺陷状态，不是套话。
- **A3 异常不伪造**：取数失败、缺陷为空、执行超限、缺版本名时，报告如实标注，无虚构数据；只读 Token 权限核验通过。
- **A4 对照实验**：取消独立统计后能观察到统计偏差，作为反例记录。

## 9. Trace 规格

- **落盘**：`traces/V1-001.json`（每个 E2E 用例一份）。
- **逐轮记录字段**：
  - `step`：步骤序号
  - `type`：`llm_reasoning` | `tool_call` | `terminate`
  - `user_input` / `llm_thought`：用户输入与 LLM 思考摘要
  - `tool_name` / `tool_args` / `tool_result`：工具调用名、入参、返回结果
  - `state_snapshot`：短期记忆 State 内容
  - `elapsed_ms`：耗时
  - `fail_reason`：失败原因（如有）
- **「Trace 可见完整链路」判定清单**：至少包含 1 次规划推理、版本信息工具调用、缺陷明细工具调用、统计工具调用、终止原因。
